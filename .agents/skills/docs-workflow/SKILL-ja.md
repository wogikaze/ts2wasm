## Mise: 完了前に実行（検証対象パスに触れた場合必須）

**完了を報告する前に、変更に一致するコマンドを実行し通過させる。** `mise`がない場合、`mise`を同じサブコマンドで使用。初回: `mise trust`（[ドキュメント](https://mise.jdx.dev/cli/trust.html)）

- 常に: `mise run fmt`（`*.md` / Rustの例に触れるため）
- デフォルトスモーク: `mise run check-repo-smoke`
- ドキュメントがテストまたはコンパイラ振る舞いを主張する場合: `mise run nextest`（Rustの例が変更された場合は`mise run clippy`も）
- `issues/`の相互リンクまたはagent/issueドキュメントを編集した場合: `mise run check-issue-health`

このskillは以下の厳格な分離を強制:

1. 最終状態プロジェクトドキュメント
2. 現在の実装状態
3. 将来の作業項目
4. 履歴/デッド状態

ドキュメントは進捗ログ、マイルストーンの残骸、陳腐化した計画、半実装のTODOの捨て場ではない。

## コアポリシー

プロジェクトドキュメントはts2wasmの意図された最終形状を記述。

通常のドキュメントページはプロジェクトのターゲット設計契約として読めるべきで、現在何が動作しているかの日記ではない。

通常のドキュメントで許可:

- プロジェクト定義
- 最終アーキテクチャ
- 意味論的契約
- ランタイムABI契約
- 機能モデル
- テストステータススキーマ
- 互換性ポリシー
- コーディング標準
- 受け入れられた設計ルール
- 安定したコマンド契約
- 期待される最終振る舞い

通常のドキュメントで禁止:

- 古い実装状態
- 「現在これは動作しない」
- 「M6でこれを実装する」
- 「一時的な回避策」
- 未解決のTODOリスト
- 進捗ログ
- 陳腐化したマイルストーン計画
- 放棄された代替案
- コピーされたissueテキスト
- 過去/現在/未来の文言の混合

## 状態分離ルール

### 最終状態ドキュメント

規範的なプロジェクト契約として最終状態ドキュメントを記述。

可能な限り現在形を使用。

良い例:

- `コンパイラはTypeScript式をJS-value IRに低減する。`
- `ランタイムは文字列値を管理ヒープオブジェクトとして表現する。`
- `WASIターゲットはマニフェストで宣言された機能のみをインポートする。`

悪い例:

- `コンパイラはTypeScript式をJS-value IRに低減する予定。`
- `現在文字列はまだ古い評価器で処理されている。`
- `TODO: 機能マニフェストサポートを追加。`
- `M6でstdinサポートを導入予定。`

将来を見据えたターゲット設計は、タスクとしてではなく受け入れられた意図されたアーキテクチャとして書かれている場合のみ許可。

### current-state.md

実際の実装状態は以下に属する:

- `current-state.md`（リポジトリルート）

このファイルを使用:

- 現在実装されているもの
- 現在部分的に実装されているもの
- 現在ブロックされているもの
- 最終状態ドキュメントと実装の間の既知のギャップ
- 現在のコマンドサポート
- 現在のカバレッジ数値
- 現在のランナー制限
- 現在サポートされていない機能

`current-state.md`のルール:

1. 事実的でなければならない
2. 削除または書き換えが容易でなければならない
3. プロジェクト目標を定義してはならない
4. 長期的な設計根拠を含んではならない
5. 未完了の作業へのissueリンクを含まなければならない
6. 最終状態ドキュメントから大きなセクションを重複してはならない
7. 実装が追いつくか乖離したときに更新しなければならない

推奨構造:

```md
# 現在の状態

最終監査: YYYY-MM-DD

## 要約

## 実装済み

## 部分的に実装済み

## 未実装

## 最終状態ドキュメントからの既知の乖離

## オープンissue

## 検証コマンド
```

### Issues

将来の作業は`issues/`に属する。

issuesを使用:

- TODOs
- マイルストーン
- 実装スライス
- 機能追加作業
- 既知のバグ
- クリーンアップ作業
- ブロックされた作業
- 延期された設計決定
- 受入基準
- 検証コマンド

ドキュメント変更が将来の作業を見つけた場合、以下のいずれかを行う:

1. 既存のissueに移動、または
2. 新しいissueファイルを作成、または
3. issueが作成されなかった理由を明示

通常のドキュメントはissue作成後にTODOを保持してはならない。

### 履歴状態

過去の状態は通常削除すべき。

通常のドキュメントで古い実装記述を「コンテキスト用」に残さない。

許可される履歴資料:

- 受け入れまたは拒否された設計決定を記録するADR
- ユーザーがまだ必要な移行ノート
- プロジェクトにchangelogがある場合のchangelogエントリ
- issueファイル内のissue議論

ルール:

1. 履歴状態は現在のように見えてはならない
2. 履歴状態はアーキテクチャ/参照ドキュメントに残ってはならない
3. 拒否された設計は最終状態ドキュメントではなくADR/issueコンテキストに属する
4. 古い状態が決定に影響しない場合、削除する

## ドキュメントタイプルール

編集前に各ドキュメントページを分類。

許可されるドキュメントタイプ:

1. プロジェクト定義
2. アーキテクチャ
3. 意味論的契約
4. ランタイムABI / 機能契約
5. テストとカバレッジ契約
6. コーディング標準
7. 現在の状態
8. ADR / 決定記録
9. ユーザー向けコマンド参照
10. コントリビューターワークフロー

各ドキュメントページは1つの主要タイプを持つべき。

混合禁止:

- アーキテクチャ + TODOリスト
- 参照 + 進捗ログ
- 現在の状態 + 最終設計
- ロードマップ + 実装ノート
- コーディング標準 + issueバックログ

## READMEルール

READMEはプロジェクトのエントリーポイント。

READMEに含めても良い:

- 1段落のプロジェクト定義
- ビルド/テストクイックスタート
- ドキュメントインデックス
- 現在の安定性警告
- `current-state.md`（リポジトリルート）へのリンク
- issuesへのリンク

READMEに含めてはならない:

- 長いロードマップ
- 陳腐化したマイルストーンテーブル
- 詳細なアーキテクチャ
- 機能TODOリスト
- 古いベンチマーク主張
- 重複したcurrent-state詳細

## クリーンアップ手順

ドキュメントを編集するとき、この監査を精神的かつ機械的に実行。

### 1. 時間カテゴリの識別

変更された各段落について、以下のように分類:

- 最終状態契約
- 現在状態の事実
- 将来のタスク
- 履歴ノート
- 根拠

次に移動:

| カテゴリ             | 行先                      |
| -------------------- | -------------------------------- |
| 最終状態契約 | 適切なドキュメントページ            |
| 現在状態の事実   | `current-state.md`（repoルート）   |
| 将来のタスク          | `issues/`                        |
| 履歴ノート      | 削除、ADR、changelog、またはissue |
| 根拠            | 説明ドキュメントまたはADR           |

### 2. 陳腐化したテキストの削除

古い振る舞いのみを説明するテキストを削除。

「以前」で陳腐化したテキストを和らげない。「履歴ノート」の下に陳腐化したテキストを残さない（まだ運用上有用でない限り）。

### 3. TODOをissuesに移動

ドキュメント内のTODOのようなテキストはすべてissueに変換しなければならない。

検索パターン:

- `TODO`
- `FIXME`
- `not yet`
- `currently`
- `temporary`
- `workaround`
- `future`
- `planned`
- `will`
- `later`
- `M[0-9]`
- `phase`
- `roadmap`
- `blocked`
- `unsupported`

issueファイルに含める:

```md
# タイトル

## 問題

## 望ましい最終状態

## 実装ノート

## 受入基準

## 検証コマンド

## 完了時に更新するドキュメント
```

issue作成後、ドキュメントTODOを以下のいずれかに置換:

- 最終状態テキスト、または
- `current-state.md`（repoルート）の短い現在状態エントリ

両方を残さない。

### 4. current-stateの同期

ドキュメントがまだ実装されていない最終振る舞いを記述する場合、`current-state.md`（repoルート）を追加または更新。

current-stateエントリは乖離を名前付け、issueにリンクすべき。

例:

```md
## 最終状態ドキュメントからの既知の乖離

- 機能マニフェスト出力は`docs/03-api-and-host-capability.md`で指定されているが、CLIはまだデフォルトでマニフェストを出力しない。
  追跡: `issues/WB-123.md`
```

### 5. 出力契約の保持

ドキュメントがスクリプト出力、TestRecord JSONL、CLI出力、カバレッジテーブルを記述するとき、ドキュメントが実際のコード/テストと一致することを確認。

current-state.md（repoルート）で現在の乖離が記録され、issueが存在しない限り、意図のみに基づいて契約ドキュメントを更新しない。

## 必須検索

ドキュメントクリーンアップを確定する前に、ターゲット検索を実行。

推奨コマンド:

```sh
rg -n "TODO|FIXME|not yet|currently|temporary|workaround|future|planned|later|roadmap|blocked|unsupported" docs README.md
rg -n "M[0-9]+|phase|milestone" docs README.md
rg -n "will|should eventually|in the future" docs README.md
rg -n "current-state|Current state|Known divergence" docs README.md issues
```

コード契約ドキュメントの場合、コード/テストも検索:

```sh
rg -n "TestRecord|suite|status|unsupported|blocked|skip-with-reason" crates scripts docs
rg -n "capability|manifest|RuntimeLinkPlan|fd_read|fd_write" crates scripts docs
rg -n "fixtures/" crates scripts docs issues
```

構造的コード契約をチェックするときは`ast-grep`を使用。

例:

```sh
ast-grep --lang rust -p 'struct $NAME { $$$ }' crates
ast-grep --lang rust -p 'enum $NAME { $$$ }' crates
```

## 検証

常に実行:

```sh
cargo fmt --all --check
```

ドキュメントのみの変更の場合、少なくとも実行:

```sh
rg -n "TODO|FIXME|not yet|currently|temporary|workaround|future|planned|later|roadmap|blocked|unsupported" docs README.md
```

ドキュメントがスクリプトまたは生成レポートに言及するとき、も実行:

```sh
scripts/check/shell-syntax.sh
```

ドキュメントがテストステータススキーマ、カバレッジ、fixture振る舞い、ランタイムABI、またはCLI契約に言及するとき、影響を受けるテストを実行:

```sh
cargo nextest run
```

最終レポートで何が実行されなかったかを正確に名前付けない限り、より小さい影響を受けるテストセットも許可。

## 一般的な罠

- READMEが第二のロードマップになる
- アーキテクチャドキュメントが現在の部分的実装を記述
- `current-state.md`が永続的なジャンク引き出しになる
- TODOがissue作成後にドキュメントに残る
- 「役に立つかもしれない」という理由で古いマイルストーンテーブルが残る
- 最終状態ドキュメントが契約を直接記述すべきときに「will」と言う
- 現在の制限が設計のようにアーキテクチャに書かれる
- issueテキストがリンクされるのではなくドキュメントにコピーされる
- ドキュメントがスクリプト/テストが強制しないカバレッジサポートを主張
- fixture移行後に古いfixtureパスがドキュメントに残る
- スクリプトオプション変更後に古いスクリプトコマンドがドキュメントに残る
- 履歴上の拒否された設計が受け入れられた設計の隣に残る
- `unsupported`と`blocked`が通過カバレッジとして記述される
- current-state事実が日付または検証コマンドなしで更新される
- ドキュメントクリーンアップがコーディング標準またはissuesを更新せずにプロジェクトポリシーを変更

## 関連スキル

- fixtures-workflow: ドキュメントがfixturesを参照するときのfixtureパス更新用
- scripts-workflow: ドキュメントがscriptsを参照するときのスクリプトコマンド更新用
- issues-workflow: TODOをドキュメントからissuesに移動用
- checklist-to-issue: チェックリスト項目をissuesに変換用

## 出力チェックリスト

最終レスポンスに含める:

1. 変更されたドキュメントファイル
2. 削除された陳腐化/履歴セクション
3. 追加または更新されたcurrent-stateエントリ
4. 将来の作業用に作成または更新されたissues
5. 更新された最終状態ドキュメント
6. README変更、または`none`
7. 契約変更、または`none`
8. 実行されたコマンド
9. 残る陳腐化リスク領域
10. 残りの作業を所有するフォローアップissues
