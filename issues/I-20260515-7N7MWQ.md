## Workstream E: Backend WAT compilation (~879 blocked → build_pass or fail+fix)

**Root cause**: BackendIo — wat2wasm compilation fails with type mismatches.

**Common errors from sample:**
```
expected [i32, i32] but got [i32]         (call $add, $array_join, $string_includes)
expected [i32, i32, i32] but got [i32, i32] (call $map_set, $string_slice, $array_reduce)
type mismatch at end of function, expected [] but got [i32]
```

These are **IR emission bugs** — the IR lowers code that calls runtime functions with wrong argument counts. Each distinct WAT error pattern corresponds to a specific lowering bug.

**Strategy**: Categorize by WAT function name:
- `$add`, `$string_includes`, `$string_slice`, `$string_substring` — arity mismatch
- `$map_set`, `$array_join` — missing argument
- `$array_reduce`, `$array_reduce_right` — initialValue argument missing
- `$array_for_each` — callback arity mismatch
- Function return type mismatch — end-of-function cleanup bug

## Workstream G: Runtime correctness (~12-13k fail → pass)

**Root cause**: Test262AssertionFailure (wrong output) and RuntimeError (execution crash).

These cases DO build successfully, meaning the compiler handles the code — but the runtime produces wrong results or crashes.

**Strategy**: This workstream naturally decreases as workstreams A-F are completed:
1. Many failures are builtins that exist but produce wrong output → fixed by implementing correct builtin (Workstream A)
2. Remaining semantic bugs are discovered by differential pass comparison

**Known patterns:**
- RuntimeError:1 (generic runtime crash) — often from unimplemented builtins or GC issues
- Test262AssertionFailure — compare Node.js oracle vs ts2wasm output differ
