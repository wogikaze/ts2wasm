## Notes

### 問題

`mise run reference-coverage -- test262` が約1600秒かかる。test262 全53,469ファイルを compile + Node/iwasm differential semantic check まで走らせる経路になっており、特に semantic phase が支配的。

### プロファイリング結果 (debug build, 12-core)

2000ファイルサンプルベースの projection (53,469 files):

| Phase | 推定時間 | 割合 |
|-------|---------|------|
| Phase 1: pre-process (read + metadata + build_source) | ~48s | ~4% |
| Phase 2: server build (batch compile, 3.4ms/file) | ~172s | ~14% |
| Phase 3: iwasm semantic check (0.3-0.5s/file × 23K passing) | ~600-1000s | ~60-80% |
| その他 (overhead, dashboard, etc.) | ~30s | ~2% |

### 根本原因

1. **Non-JSONL aggregate path が legacy**: `scripts/run/reference-coverage.py:2545` 以降のコードが metadata cache なし、batch_size=200、semantic worker 分離なし。
2. **JSONL path (`--jsonl`) は最適化済み**: metadata cache、prepare worker 48並列、semantic worker 24並列、batch_size=1000、oracle_skip最適化を持つ。
3. **iwasm が debug build で 0.3-3.5s/file**: 小さいWASM(56KB)で0.3s、大きいWASM(300KB)で3.5s。
4. **short-lived process の大量生成**: passing ~23K件分の iwasm (+必要なら node) 起動。

### 対応内容 (この issue)

**P0**: test262 通常 path を JSONL path に統一
- `reference-coverage test262` は内部的に常に JSONL runner を使う
- 後方互換性のため legacy key=value summary を stdout に出力
- これにより metadata cache, 並列 prepare, 適切な batch_size(=1000) が自動適用される

**P1**: `--detail` を JSONL post-render に変更
- 従来: aggregate path 内で suite_detail_rows を収集 (再実行相当)
- 新: JSONL ファイルから最後に読み出して表示
- `--detail` のオーバーヘッドが +5% 以内に

**P2**: Phase profiler 追加
- `artifacts/coverage/results/test262-profile.json` に各 phase の wall time を出力
- 計測項目: prepare_ms, server_build_ms, server_fallback_batches, iwasm_processes, node_processes

### 残タスク (別 issue)

- **P3**: iwasm-first semantic ordering (iwasm が失敗したら Node 不要)
- **P4**: strict / fast / build-only の semantic mode 分離
- **P5**: server worker pool 永続化 (batch ごとに thread pool を作らない)
- **Release build**: `cargo build --release` で ts2wasm を build すると server compile ~2-3x 高速化

- [ ] `artifacts/coverage/results/test262-profile.json` が生成される
