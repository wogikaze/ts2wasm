## Notes

### Fixed: Function.prototype.call/apply on runtime function value locals (2026-05-20)

**Problem**: `lower_function_call_apply_method` only handled `ResolvedExpr::Ident` that
resolved to a compile-time known FuncId (function declarations). When a function was
stored in a local variable (e.g., `let g = f; g.call(undefined)`), `resolve_func`
failed, and the call fell through to class dispatch which returned
`issue-211: unknown receiver class for method 'call'`.

**Fix**: Extended `lower_function_call_apply_method` in `crates/ir/src/lowered/resolver/call/method.rs`
to handle function-valued locals by emitting a `HeapClosureCall` with the function
value, thisArg, and explicit arguments. The runtime HeapClosureCall dispatches based
on the function's tag (DirectLocalToken or closure) and passes thisArg as the first
user arg (the receiver slot).

**Pattern handled**: `func.call/receiver, ...args/` and `func.apply/receiver, argsArray/`
where `func` is any runtime function value (local variable, function expression, etc.).

**Patterns NOT handled (remaining)**:
- `Function.prototype.bind` on runtime function values (requires WAT closure creation)
- `Function.prototype.toString` on non-ident receiver function values
- `Function.prototype[Symbol.hasInstance]` on runtime function values

### Added Function host infrastructure for runtime apply/call (2026-05-20)

**Problem**: `collection_method_runtime_fn` did not route Function.prototype.apply
for dynamic function values. The IR had no RuntimeFn variant for function calling
with a receiver and args array. test262 Function built-ins fail at runtime.

**Fix**: Added complete Function host infrastructure:
- Added HostImport variants: FunctionCompile, FunctionCall, FunctionCallMethod,
  FunctionConstruct, EvalDirect, EvalIndirect
- Added RuntimeFn variants: FunctionCallMethodHost (for apply), FunctionCallHost,
  FunctionCompileHost, FunctionConstructHost, EvalDirectHost, EvalIndirectHost
- Route `("Function", "apply")` -> `FunctionCallMethodHost` and catch-all `"apply"` -> `FunctionCallMethodHost`
- Route `("Function", "call")` -> `HeapClosureCall` and catch-all `"call"` -> `HeapClosureCall`
- Route `("Function", "toString")` -> `ObjectToString`
- Added WAT emitters for all host functions in runtime/host/emit.rs
- Added dispatch arms in runtime_dispatch_host.rs
- Added capability variants and wired through link_plan and manifest

**Files changed**: 10 files, +291/-3 lines

### 2026-06-14: Fix native emitter link plan mismatch for Unary Not

**Problem**: The native module emitter handles `!x` (Unary Not) inline with `I32Eqz`,
but the link plan collector (`runtime_link_plan.rs`) expected `RuntimeFn::Not` to be
called. This caused a test mismatch: `native_module_declares_exact_required_runtime_function_symbols`
expected `{Copy, TruthyBool, Not, AllocHeap, ObjectKeys}` but only got `{AllocHeap}`.

**Fix**: Updated `collect_required_runtime_expr` in `runtime_link_plan.rs` to not add
`RuntimeFn::Not` for `UnaryOp::Not`, since the native emitter handles it inline with
`I32Eqz`. This mirrors the existing pattern for `BitwiseNot` which is also handled by the
native binary path.

**Note**: Using plain `I32Eqz` for `!` is incorrect for NULL (tag=1) and FALSE (tag=2)
values since they're falsy but non-zero. The `I32Eqz` check only works correctly when the
input value is guaranteed to be boolean (tag 0 or 3). For general runtime values, the
native emitter should call `$not` (which properly uses `$truthy_bool`). This remains a
known issue for a follow-up fix.

**Files changed**:
- `crates/backend-wasm/src/runtime_link_plan.rs`: Remove `RuntimeFn::Not` from unary
  `Not` collector (native emitter handles inline)
