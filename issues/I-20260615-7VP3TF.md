## Notes

### Impact (2026-06-15)

Discovered during Error/AggregateError test262 failure analysis. 3 Error tests require `Object.prototype.toString` to correctly report `[object Error]` for Error instances.

#### Affected tests (3 total)

1. **`Error/tostring-1.js`** — `new Error().toString()` returns `"Error"` (via Error.prototype.toString), then after `Error.prototype.toString = Object.prototype.toString`, returns `"[object Error]"` (via Object.prototype.toString with [[ErrorData]])

2. **`Error/tostring-2.js`** — Same but with `Error()` (no new)

3. **`Error/prototype/no-error-data.js`** — Error.prototype does NOT have [[ErrorData]], so `Object.prototype.toString.call(Error.prototype)` returns `"[object Object]"`. Requires `Object.defineProperty` + `Symbol.toStringTag` support.

#### Status: WAT runtime fix done (2026-06-15)

Added `[[ErrorData]]` detection to `$object_to_string` in `crates/backend-wasm/src/runtime/object/emit.rs`:
- Compares object's prototype pointer against enabled `$error_proto_*` globals
- Returns `[object Error]` if match, `[object Object]` otherwise
- Error.prototype itself correctly returns `[object Object]`

#### Remaining blockers

1. **IR compile-time ErrorToString bypass**: `new Error().toString()` is compiled to a direct `RuntimeFn::ErrorToString` call, never reaching `$object_to_string`. Fix options:
   - Make IR NOT resolve Error.toString for non-ident receivers (risky — could break working code)
   - Add `Symbol.toStringTag` check to `$error_to_string` and route to `$object_to_string` when appropriate
   - The test assigns `Error.prototype.toString = Object.prototype.toString` at runtime — IR cannot know this

2. **Symbol.toStringTag support**: `no-error-data.js` uses `Object.defineProperty(Error.prototype, Symbol.toStringTag, { value: null })` which requires both `Object.defineProperty` and `Symbol` support.

3. **Object.defineProperty**: Required for `no-error-data.js` (tracked in separate issue I-20260615-8WMZG9)
