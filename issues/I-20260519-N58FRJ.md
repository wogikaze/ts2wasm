## Notes

### globalThis.parseInt routing fix (2026-05-20)

Fixed `globalThis.parseInt(...)` routing:
- Added `globalThis` block to `resolve_method_to_runtime_fn` in `program_builtins.rs` — routes `globalThis.parseInt/parseFloat/isNaN/isFinite/encodeURI/etc` to corresponding `RuntimeFn` variants
- Added `"globalThis"` to `is_static_call` list in `method.rs` — prevents `globalThis` from being pushed as a method receiver argument
- Previously, `globalThis.parseInt("42")` hit `resolve_local("globalThis")` which failed with `[UnresolvedName/lowering]`

Validation:
- `globalThis.parseInt("42")` → 42 (runtime)
- `globalThis.parseInt("0xFF", 16)` → 255 (runtime)
- `cargo nextest run -p ts2wasm-cli --test builtin_methods -- build_smoke_global_parseint` → 2/2 pass

Committed in `9dbf19d62` (auto-commit). Remaining 33 parseInt failures need separate investigation (see test262 results).

### Number tag short-circuit fix (2026-05-21)

Fixed the main WAT-level parseInt bug: `$parse_int` previously short-circuited for Number-tagged inputs, returning the tagged number as-is instead of converting to string per ECMAScript spec Step 1 (ToString). This caused:

- `parseInt(Infinity)` returned Infinity instead of NaN
- `parseInt(-Infinity)` returned -Infinity instead of NaN  
- `parseInt(-0)` returned -0 instead of 0 (strict equality mismatch)

Fix: replaced `(then (return (local.get $s)))` with a call to `$number_to_string` to convert the number to its decimal string representation, then continue through the normal string parsing path. This correctly handles all Number inputs per spec:

- `parseInt(NaN)` → ToString(NaN) = "NaN" → NaN ✓ (unchanged)
- `parseInt(Infinity)` → ToString(Infinity) = "Infinity" → NaN ✓ (fixed)
- `parseInt(-0)` → ToString(-0) = "0" → 0 ✓ (fixed)
- `parseInt(42)` → ToString(42) = "42" → 42 ✓ (unchanged)

**Limitations (not fixed in this round):**
- Non-String/Number inputs (Object, Boolean, null, undefined) still return NaN directly instead of converting via ToString. For most cases the result is NaN either way, but `new Number(-1)` → ToString → "-1" → -1 would be wrong (returns NaN).
- Property descriptor tests (`prop-desc.js`, `not-a-constructor.js`, `A9.5.js`) fail due to missing test262 harness support, not parseInt WAT bugs.
- Tests using `includes: [propertyHelper.js]` or `includes: [isConstructor.js]` require harness support beyond runtime scope.
- Temporal remains a large API (251 failures) requiring its own dedicated issue.

**Remaining estimated parseInt WAT-level failures after fix:** ~27 (from 33). The remaining 6 were due to the Number tag short-circuit.
