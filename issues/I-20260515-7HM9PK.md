Title: Architecture decision: Unicode normalize strategy (host shim vs WAT-embedded data)
Summary: Decide whether String.prototype.normalize (non-ASCII) should use Node.js host shim or embedded Unicode normalization tables.

## Notes

### 2026-05-15 decision

**Decision: Host shim (Node.js/`$host_string_normalize`).**

Rationale:
1. **Precedent**: All Date methods (`host_date_utc`, `host_date_to_iso_string`, `host_date_get_timezone_offset`) use Node.js host shims. Unicode normalization follows the same pattern.
2. **Binary size**: Embedding Unicode Character Database (UCD) normalization tables (NFD, NFKC, NFKD composition/decomposition maps) would add ~500KB+ to the WASM binary, which is prohibitive.
3. **Complexity**: The normalization algorithm (UAX #15) requires recursive composition/decomposition with Hangul syllable processing — a significant implementation effort in WAT.
4. **Runtime**: The host shim approach delegates to Node.js `String.prototype.normalize()`, which is already spec-compliant and free.

**Action**: File a new issue to implement `$host_string_normalize` host shim + WAT dispatch, referencing this decision.
