## Notes

## Audit Findings (2026-05-21)

### What is already implemented

**Parser**: `import("...")` is recognized and rewritten to `__ts2wasm_dynamic_import("...")` Call expression (`crates/frontend/src/parser/expressions_main.rs:2213-2228`).

**Name resolution**: `__ts2wasm_dynamic_import` is registered as an unshadowable intrinsic (`crates/resolve/src/name_resolver.rs:74`).

**Builtin resolution**: `__ts2wasm_dynamic_import("string_literal")` is lowered to `ResolvedExpr::ModuleLoad { is_dynamic_import: true }` (`crates/ir/src/builtin_resolver.rs:2104-2116`).

**IR lowering**: `ModuleLoad { is_dynamic_import: true }` is lowered to `LoweredExpr::ModuleLoad { kind: DynamicImport }` (`crates/ir/src/lowered/resolver/expr/mod.rs:164-176`).

**WAT emission**: Dynamic import wraps `$module_require` result in `$promise_resolve` to return a Promise (`crates/backend-wasm/src/expr_emit.rs:290-306`).

**Runtime functions**: `$module_require` (module cache lookup/create), `$promise_resolve` (fulfilled promise creation), `$promise_then` (chaining), `$task_poll`/`$task_result` (synchronous async poll) are all implemented.

**Default exports**: `export default expr` is handled by the compiler's lower stage (`crates/compiler/src/stages/lower.rs:299-313`).

**Static default imports**: `import x from './foo'` works via the module rewrite system (`static_imports::lower_static_named_import_bindings_for_build`).

**Tests**: build_smoke for dynamic-import.ts passes. IR lowering test preserves DynamicImport kind.

### What is missing

**Module graph doesn't track dynamic imports (CRITICAL GAP)**: The module graph builder (`crates/compiler/src/module_graph.rs`) only collects specifiers from static import/export statements via `collect_static_module_specifiers`. Dynamic `import()` calls (`__ts2wasm_dynamic_import("...")`) are NOT recognized. This means:

- The imported module is never parsed or compiled
- `$module_require(id)` at runtime returns a fresh empty exports object (the module was never initialized)
- The fix is to recursively walk the program tree for `__ts2wasm_dynamic_import(...)` calls and add their targets to the module graph

**test262 `dynamic-import` feature flag missing**: `dynamic-import` is not in the `KNOWN_FEATURES` list of the test262 preprocessor. This causes 355 test262 tests with `features: [dynamic-import]` to fail with `UnsupportedSyntax` diagnostic. The fix is to add `("dynamic-import", "I-20260519-VCSBRP")` to the list.

**No runtime (node_diff) test**: The existing build_smoke test only verifies compilation succeeds, not runtime correctness. A node_diff test comparing iwasm output with Node.js output would verify that dynamically imported modules' exports are accessible.

### Changes made in this audit

1. **`crates/compiler/src/module_graph.rs`**: Added `collect_dynamic_import_specifiers` that recursively walks the program tree for `__ts2wasm_dynamic_import("...")` calls and registers their targets as module dependencies. This ensures the imported modules are compiled and their exports are available at runtime.

2. **`crates/compiler/src/test262_preprocessor.rs`**: Added `("dynamic-import", "I-20260519-VCSBRP")` to `KNOWN_FEATURES` to unblock the 355 test262 tests.

### Remaining work

- Runtime test262 failures: Even with the feature flag, many dynamic import tests may fail at runtime due to edge cases (non-string arguments, error handling, module namespace object shape, etc.)
- Non-string-literal `import(expr)`: The builtin resolver only accepts string literal arguments. Template literals or variable imports would fail.
- Module namespace object: The current `$module_require` returns a plain object, not a Module Namespace Exotic Object with [[Module]] internal slot.
